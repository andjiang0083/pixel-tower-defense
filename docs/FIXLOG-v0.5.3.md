# FIXLOG v0.5.3 — 性能筛查：帧预算到底花在哪；以及把"出兵上限"还回去

> 触发：用户听完 v0.5.2 的修法后直接点破 ——
> *"我建议也做一次性能筛查和优化，没理由那么简单的塔防游戏，需要调整出兵的策略来
> 规避性能瓶颈。复杂的 gba 模拟器也有更复杂的塔防也顶得住。"*
> 结论：**他说得对。** v0.5.2 里的 `OVERLAP_FIELD_MAX=16`（场上超过 16 只就不压叠）
> 是拿 PC 仿真的 fillRect 次数当负载代理量拍出来的出兵上限 —— 不是修 bug，是绕开性能。
> 本轮先量真机、再修渲染，然后把这个上限删掉。
> 版本：v0.5.2 → **v0.5.3**。

---

## 一、先量（只认负载态仪表）

真机上加了默认关闭的性能探针（`PTD_PERF_PROBE`，见 `src/main.cpp` / `src/gfx_m5gfx.h`）
＋**确定性合成负载**（`PTD_PERF_SPAWN=N`：直接进 L10、把场上敌人钉在 N 只、血量钉在中后期档、
生命锁死 ⇒ 不需要任何人碰屏幕就能长时间稳定重载）。分段计时拆到
`erase / tower / enemy / bullet / fx / hud`，并数**提交次数**与**像素数**。

### 1. 48 只同屏、无塔（先排除"敌人多就一定慢"）

```
fps=30.3 frame=33.0ms | upd=0.04ms draw=5.5~8.6ms sfx=0.005ms
rects≈500/帧 px≈80k/帧
```
**帧时间正好卡在 33ms 节拍上 = 循环在空转等下一帧。48 只本身离预算还远。**

### 2. 48 只 + 20 座 1 级塔（真实重载）

```
fps=30.3 frame=33.0ms | draw=17~23ms rects≈1200 px≈190k snd≈20/秒
```

### 3. 最坏档：44~48 只（含 4 只 BOSS）+ 20 座 **3 级**塔

```
fps=27.6~30.2 frame=33~36ms | draw=34.8ms（**超预算，单帧峰值 40ms**）
  seg | erase=24.95  tower=3.61  enemy=6.00  bullet=0.07  fx=0.08  hud=0.02  (ms/帧)
```
⇒ **擦脏格占渲染的 70%**，而且 `rects≈2100/帧` 里 `small≈1700` 次是 ≤64px 的碎块。

### 4. 分辨"带宽"还是"调用次数"（去掉抖动纹理 + 网格线，像素几乎不变）

| | 现状 | 实验档 |
|---|---|---|
| fillRect/帧 | 1991~2156 | **688~734** |
| erase | 22~25ms | **9~13ms** |
| draw 总 | 33~36ms（掉帧） | **21~24ms（30.3fps 稳）** |
| px/帧 | ~300k | ~230k |

**像素几乎没变、调用数掉 3 倍、时间掉 2.5 倍 ⇒ 贵的是"碎块税"（每次调用的固定开销 +
缓存行读写回 + PSRAM 帧缓冲与 DSI 扫描抢带宽），不是搬运量。**
（一格 40×40 用 fillRect 拼抖动纹要 **25+ 次**调用；路径边缘描边再加 ~4 次。）

## 二、修法：一格一次块拷贝（背景格子缓存）

- `Gfx` 增一个原语 `pushImage(x,y,w,h,const uint16_t*)`（块拷贝），提供**默认逐像素实现**
  ⇒ 没声明能力的后端不覆写、也不调用，**零位移**（同 `PTD_HAS_CJK` 的能力宏纪律）。
- `PTD_BG_TILE_BLIT` 能力宏（profile 提供：tab5=1 / claw4=0，见 `tools/layout.py`）。
- `render.h`：每类**变体**的 40×40 格子预先画一次（用**同一份** `drawCellBaseAt`，因此
  逐像素相同），擦格时一次 `pushImage` 写回整格。变体键 = `(path|blocked|棋盘奇偶, 四邻是否路)`，
  L10 实测 **18 类**（上限 24 类 = 76.8KB，存片内 SRAM 优先，失败退 PSRAM，再失败退逐矩形）。
- 主题随关卡变 ⇒ 缓存按 `g_lv` 失效重建；变体超限/分配失败 ⇒ **静默退回逐矩形**（慢但正确）。

### 正确性闸（这条比性能更重要）

`sim/run.cpp §14c`：同一帧分别用"块拷贝路径"与"逐矩形路径"渲染，**地图区逐像素比对**。
> `[bg-tile] 块拷贝 vs 逐矩形：地图区逐像素比对 0 处不同（tiles=18 类）`

为什么必须自己立这条：优化的是画法，一旦漂移，症状是"某几个格子的纹理不对"这种最难发现的
坏法，而**性能读数只会变好看**。缓存用的是同一个绘制函数 ⇒ 逐像素相同是构造保证，这条断言是牙齿。

### 修后（同一最坏档，真机）

| | 修前 | 修后 |
|---|---|---|
| fillRect/帧 | 1991~2156 | **415~573** |
| erase 段 | 22~25ms | **7.6~12.6ms** |
| draw 总 | 33~36ms（掉帧） | **16.8~23ms** |
| fps | 27.6~30.2 | **30.3 稳（frame=33.0ms）** |

## 三、把出兵上限删掉（用户点破的那一条）

- 删 `OVERLAP_FIELD_MAX`（`layout.py` / `config_gen.h` / `game.h` 判据一并删）。
- **保留** v0.5.2 的真修复：压叠只看**本波出生的幸存者**（`waveTag`）≤ 本波一半 ——
  那是用户报的"第 2 波没打完就自动开第 3 波"的根因，与性能无关。
- 断言改造（`sim/run.cpp`）：
  - §14③ 由"场上 ≥16 不许压叠"改成**反向门禁**：本波只剩 2 只时，哪怕场上堆着 16 只
    上一波的残留，**也照样必须压叠**（防止有人再把"等全清"塞回来）。
  - §14b 由"峰值 ≤32"改成 ① 不得触到数组硬顶 ② **压叠不得发生在"本波过半存活"时**
    （= 用户报的 bug 本身，逻辑判据，与性能无关）。

## 四、留给下一轮的（不吹）

1. erase 仍是最大段（~10ms/100 格）。当前 30fps 稳，但**不是零成本**：真要再挖，方向是
   "按实体包围盒擦（只重画真正变过的像素）"而不是整格 40×40 —— 那需要全图背景缓存
   （1.43MB PSRAM）+ 把脏区机制从"格"改成"矩形"，动的是共享引擎，另起一轮。
2. 音频段目前 ≤0.08ms/帧（探针实测），**不是**瓶颈；`playRaw(force)` 的阻塞风险仍待真机
   长时间观察（本轮负载下没出现）。
3. Claw4 侧 `PTD_BG_TILE_BLIT=0`：它的渲染写法与帧缓冲管理不同，要单独量过再开
   （能力宏已就位，开法是改 `layout.py` 一格 + 在它 BSP 里覆写 `pushImage`）。
4. 环境坑（与本项目无关但会浪费一轮）：`pio` 会间歇性**重新解包** `framework-arduinoespressif32`
   与 `...-libs`，与编译并发时就报 `Print.h/Stream.h: No such file or directory`。
   症状像仓库坏了，其实是包在重装 —— 先 `pio pkg install -e tab5` 再构建即可。

## 五、经验

1. **别拿另一个环境上的代理量当性能判据**。"每帧 fillRect 次数"在 PC 仿真上是方便的代理量，
   但它没说清"这台机器能不能扛住"；本轮实测：48 只同屏只花 8ms/33ms，而**用户报的"死机"
   另有出处**（碎块税在满场+BOSS 时才爆）。
2. **先分辨"带宽"还是"调用次数"**：去掉纹理（像素几乎不变）就能一刀切开这两种病因。
   这次是调用次数（3 倍调用 → 2.5 倍耗时）。
3. **性能优化必须配逐像素相等断言**：缓存/批处理类改动的坏法是"画错"，而画错在性能读数上
   看不出来。用同一个绘制函数生成缓存 + 双路径比对，是既便宜又硬的形态。
4. **"少放敌人"不是性能优化**：帧预算是渲染的事，不是波次的事。凡是把性能问题转嫁成
   玩法限制的判据，都要在量完之后删掉并写成门禁（防止它悄悄回来）。
