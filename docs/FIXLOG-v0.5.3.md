# FIXLOG v0.5.3 — 性能筛查：帧预算到底花在哪；以及把"出兵上限"还回去

> 触发：用户听完 v0.5.2 的修法后直接点破 ——
> *"我建议也做一次性能筛查和优化，没理由那么简单的塔防游戏，需要调整出兵的策略来
> 规避性能瓶颈。复杂的 gba 模拟器也有更复杂的塔防也顶得住。"*
> 结论：**他说得对。** v0.5.2 里的 `OVERLAP_FIELD_MAX=16`（场上超过 16 只就不压叠）
> 是拿 PC 仿真的 fillRect 次数当负载代理量拍出来的出兵上限 —— 不是修 bug，是绕开性能。
> 本轮先量真机、再修渲染，然后把这个上限删掉。
> 版本：v0.5.2 → **v0.5.3**。

## 一、先量（只认负载态仪表）

真机上加了默认关闭的性能探针（`PTD_PERF_PROBE`，见 `src/main.cpp` / `src/gfx_m5gfx.h`）
＋**确定性合成负载**（`PTD_PERF_SPAWN=N`：直接进 L10、把场上敌人钉在 N 只、血量钉在中后期档、
生命锁死 ⇒ 不需要任何人碰屏幕就能长时间稳定重载）。分段计时拆到
`erase / tower / enemy / bullet / fx / hud`，并数**提交次数**与**像素数**。

### 1. 48 只同屏、无塔（先排除"敌人多就一定慢"）

```
fps=30.3 frame=33.0ms | upd=0.04ms draw=5.5~8.6ms sfx=0.005ms
rects≈500/帧 px≈80k/帧
```
**帧时间正好卡在 33ms 节拍上 = 循环在空转等下一帧。48 只本身离预算还远。**

### 2. 48 只 + 20 座 1 级塔（真实重载）

```
fps=30.3 frame=33.0ms | draw=17~23ms rects≈1200 px≈190k snd≈20/秒
```

### 3. 最坏档：44~48 只（含 4 只 BOSS）+ 20 座 **3 级**塔

```
fps=27.6~30.2 frame=33~36ms | draw=34.8ms（**超预算，单帧峰值 40ms**）
  seg | erase=24.95  tower=3.61  enemy=6.00  bullet=0.07  fx=0.08  hud=0.02  (ms/帧)
```
⇒ **擦脏格占渲染的 70%**，而且 `rects≈2100/帧` 里 `small≈1700` 次是 ≤64px 的碎块。

### 4. 分辨"带宽"还是"调用次数"（去掉抖动纹理 + 网格线，像素几乎不变）

| | 现状 | 实验档 |
|---|---|---|
| fillRect/帧 | 1991~2156 | **688~734** |
| erase | 22~25ms | **9~13ms** |
| draw 总 | 33~36ms（掉帧） | **21~24ms（30.3fps 稳）** |
| px/帧 | ~300k | ~230k |

**像素几乎没变、调用数掉 3 倍、时间掉 2.5 倍 ⇒ 贵的是"碎块税"（每次调用的固定开销 +
缓存行读写回 + PSRAM 帧缓冲与 DSI 扫描抢带宽），不是搬运量。**
（一格 40×40 用 fillRect 拼抖动纹要 **25+ 次**调用；路径边缘描边再加 ~4 次。）

## 二、修法：一格一次块拷贝（背景格子缓存）

- `Gfx` 增一个原语 `pushImage(x,y,w,h,const uint16_t*)`（块拷贝），提供**默认逐像素实现**
  ⇒ 没声明能力的后端不覆写、也不调用，**零位移**（同 `PTD_HAS_CJK` 的能力宏纪律）。
- `PTD_BG_TILE_BLIT` 能力宏（profile 提供：tab5=1 / claw4=0，见 `tools/layout.py`）。
- `render.h`：每类**变体**的 40×40 格子预先画一次（用**同一份** `drawCellBaseAt`，因此
  逐像素相同），擦格时一次 `pushImage` 写回整格。变体键 = `(path|blocked|棋盘奇偶, 四邻是否路)`，
  L10 实测 **18 类**（上限 24 类 = 76.8KB，存片内 SRAM 优先，失败退 PSRAM，再失败退逐矩形）。
- 主题随关卡变 ⇒ 缓存按 `g_lv` 失效重建；变体超限/分配失败 ⇒ **静默退回逐矩形**（慢但正确）。

### 正确性闸（这条比性能更重要）

`sim/run.cpp §14c`：同一帧分别用"块拷贝路径"与"逐矩形路径"渲染，**地图区逐像素比对**。
> `[bg-tile] 块拷贝 vs 逐矩形：地图区逐像素比对 0 处不同（tiles=18 类）`

为什么必须自己立这条：优化的是画法，一旦漂移，症状是"某几个格子的纹理不对"这种最难发现的
坏法，而**性能读数只会变好看**。缓存用的是同一个绘制函数 ⇒ 逐像素相同是构造保证，这条断言是牙齿。

### 修后（同一最坏档，真机）

| | 修前 | 修后 |
|---|---|---|
| fillRect/帧 | 1991~2156 | **415~573** |
| erase 段 | 22~25ms | **7.6~12.6ms** |
| draw 总 | 33~36ms（掉帧） | **16.8~23ms** |
| fps | 27.6~30.2 | **30.3 稳（frame=33.0ms）** |

## 三、把出兵上限删掉（用户点破的那一条）

- 删 `OVERLAP_FIELD_MAX`（`layout.py` / `config_gen.h` / `game.h` 判据一并删）。
- **保留** v0.5.2 的真修复：压叠只看**本波出生的幸存者**（`waveTag`）≤ 本波一半 ——
  那是用户报的"第 2 波没打完就自动开第 3 波"的根因，与性能无关。
- 断言改造（`sim/run.cpp`）：
  - §14③ 由"场上 ≥16 不许压叠"改成**反向门禁**：本波只剩 2 只时，哪怕场上堆着 16 只
    上一波的残留，**也照样必须压叠**（防止有人再把"等全清"塞回来）。
  - §14b 由"峰值 ≤32"改成 ① 不得触到数组硬顶 ② **压叠不得发生在"本波过半存活"时**
    （= 用户报的 bug 本身，逻辑判据，与性能无关）。

## 四、留给下一轮的（不吹）

1. erase 仍是最大段（~10ms/100 格）。当前 30fps 稳，但**不是零成本**：真要再挖，方向是
   "按实体包围盒擦（只重画真正变过的像素）"而不是整格 40×40 —— 那需要全图背景缓存
   （1.43MB PSRAM）+ 把脏区机制从"格"改成"矩形"，动的是共享引擎，另起一轮。
2. 音频段目前 ≤0.08ms/帧（探针实测），**不是**瓶颈；`playRaw(force)` 的阻塞风险仍待真机
   长时间观察（本轮负载下没出现）。
3. Claw4 侧 `PTD_BG_TILE_BLIT=0`：它的渲染写法与帧缓冲管理不同，要单独量过再开
   （能力宏已就位，开法是改 `layout.py` 一格 + 在它 BSP 里覆写 `pushImage`）。
4. 环境坑（与本项目无关但会浪费一轮）：`pio` 会间歇性**重新解包** `framework-arduinoespressif32`
   与 `...-libs`，与编译并发时就报 `Print.h/Stream.h: No such file or directory`。
   症状像仓库坏了，其实是包在重装 —— 先 `pio pkg install -e tab5` 再构建即可。

## 五、经验

1. **别拿另一个环境上的代理量当性能判据**。"每帧 fillRect 次数"在 PC 仿真上是方便的代理量，
   但它没说清"这台机器能不能扛住"；本轮实测：48 只同屏只花 8ms/33ms，而**用户报的"死机"
   另有出处**（碎块税在满场+BOSS 时才爆）。
2. **先分辨"带宽"还是"调用次数"**：去掉纹理（像素几乎不变）就能一刀切开这两种病因。
   这次是调用次数（3 倍调用 → 2.5 倍耗时）。
3. **性能优化必须配逐像素相等断言**：缓存/批处理类改动的坏法是"画错"，而画错在性能读数上
   看不出来。用同一个绘制函数生成缓存 + 双路径比对，是既便宜又硬的形态。
4. **"少放敌人"不是性能优化**：帧预算是渲染的事，不是波次的事。凡是把性能问题转嫁成
   玩法限制的判据，都要在量完之后删掉并写成门禁（防止它悄悄回来）。

## 六、补记：真机"紫色"——块拷贝的字节序（性能修复的回归）

**症状**（用户真机反馈）：怪物走过的地方变成紫色。

紫色 = 红蓝互换的典型症状，而且**只出现在"擦格"这条路走过的地方** —— 因为
v0.5.3 的性能修复只改了擦格：从"逐矩形重画"改成"一格一次块拷贝"（`pushImage`）。
其余单色块仍走 `fillRect`，颜色一直是对的。

**根因**（LGFX 源码级）：16 位深度在 LGFX 里有**两套字节序**：

| 枚举 | 值 | 含义 |
| --- | --- | --- |
| `rgb565_2Byte` | `16` | `get_depth<uint16_t>()` 的默认认定 —— "数据**字节已交换**" |
| `rgb565_nonswapped` | `16 \| 0x0100` | Tab5 DSI 面板的实际写深度（`Panel_DSI.inl` 的 `_write_depth`） |

于是 `d_->pushImage(x, y, w, h, const uint16_t*)` 会把我的标准 565 数据**再交换一次**
⇒ 红蓝互换。而 `fillRect` 走的是另一条转换，所以只有块拷贝路径变紫。

**修法**：在**建缓存那一次**把字节序摆正（`Gfx::prepareTile` 后端钩子，
M5GFX 覆写为逐像素交换），块拷贝本身仍是裸 `pushImage` ⇒ 每帧零成本。
`prepareTile` 与调用点都在 `#if PTD_BG_TILE_BLIT` 内（Claw4 没有这个能力宏 ⇒ 零位移）。

**设备侧自检（这条比"看着不对再说"重要）**：PC 仿真（`GfxFb`）有自己的 16bpp 约定，
**验不了 M5GFX 的转换**。所以加了一次性探针档自检（`PTD_BG_TILE_SELFCHECK`，
只在探针档编进来）：把同一份 8×8 已知颜色图案分别用 ①`fillRect`（参考）②各候选
`pushImage` 形态画上屏，再用 `readPixel` 逐点读回比对。实测：

```
BLITCHK ref self-test: 0/64 mismatch (readPixel ok)   ← 参考自证：读数可用
BLITCHK v0    plain(2Byte)   mism=64  exp=F800 got=00F8   ← 整像素字节互换
BLITCHK v1    selfswap+plain mism= 0
BLITCHK v9    PRODUCTION     mism= 0                        ← 生产路径
```

> 同一轮里 `TITLEINK`（双语标题上屏自检）也踩了两次**探针自己错**：先用"通道窗口"
> 猜金色（金在 565 里绿场是 51，不在窗口内 ⇒ 读回全 0），又把调色板值当 RGB888 换算
> （期望值算成 `0x07ED`，而屏上读回就是 `0xFE69`）。两次看起来都像"产品坏了"。
> **确定底色只能靠"画已知色 → 读回原始值"，探针里不做任何颜色换算。**

## 七、补记：中文界面回归（阶段二：入口 + 几何 + 门禁）

阶段一把双语表和字库按能力宏 `PTD_HAS_CJK` 恢复了，但**入口还是断的**：标题界面
没有语言按钮、NVS 里没有 `lang`。这一轮补齐：

- **语言按钮**（`render.h` 画 / `actions.h` 命中，几何同 MUTE 惯例作唯一真源）：
  纵向位置**从当前布局链推导**，不再抄 v0.4.4 的写死值 302/330 —— v0.5.1 起标题布局
  全部比例化，"写死值"就是"改一处必漏一处"的老病根。
- **NVS `lang`** 存读 + 启动横幅印 `lang=EN|CN`（真机排障时"用户看到的是哪种语言"
  直接影响判断）。
- **中文副标题必须走 `TR(STR_TITLE_CN)`**：硬编码中文不进 `STR_CN` 表，`gen_cnfont`
  就收不到字（v0.4.2 缺 3 字的成因）。
- **缺字门禁**（仿真）：把 `STR_CN` 全表每条都渲染一遍，缺字计数器必须为 0。
  表是字库的唯一输入，"全表渲染无缺字"即覆盖证明。实测 99 字形、缺字 0。
- **文本适配按语言循环**（`for (lang)` 两种语言各跑一遍 `checkUiTextFit`）：
  中文 17px/字、不随 scale 缩，与英文排版完全不同，只测一种 = 放过另一套真实排版。
  ⚠️ v0.5.1 曾把这个循环删掉（理由是"在测一个不存在的分支"）—— 那是**把测试改成
  实现的样子**，而不是让实现满足测试。
- 这条循环立刻抓到一个真缺陷：**无尽模式 BEST 块压掉"波次"标签**（中文"最高"34px
  比英文"BEST" 24px 宽 10px）。修法不是"中文模式特判"，而是**按最宽的语言留位**
  （HUD 常驻、语言运行时可切，切一次重排整个 HUD 不现实）。

真机自检（同一轮探针）：

```
TITLEINK ctl_gold=11200                              ← 控制组：读回可用
TITLEINK lang=EN sub_ink=0   clusters=0 gold_en=992 gold_cn=0
TITLEINK lang=CN sub_ink=368 clusters=4 gold_cn=992 gold_en=0
```

`clusters=4` 就是"像素塔防"四个字真的画在面板上了，`sub_ink=368` 与仿真逐字一致。

## 八、补记：把"另一台机器"钉成门禁（Claw4 零位移）

tab5 与 claw4 共用同一份 `src/*.h`（只差 `build/<profile>/config_gen.h`）。为 Tab5
修东西时**顺手改到共享层**，会让 Claw4 固件跟着位移 —— 那是另一台机器、另一批
用户的固件。v0.5.0 的教训更贵：为了 Claw4 的 720 窄屏在共享层删掉中文链路，
Tab5 的中文能力被连带干掉。

本轮把证明做成**机器可判的门禁** `tools/claw4_isolation.py`：把共享文件按 claw4
profile 预处理一遍，逐字节比对基线哈希（`docs/claw4-isolation.sha256`）。
预处理输出相同 ⇒ 编译器看到的源码相同 ⇒ 目标码必然相同（比反汇编更早、更硬）。
本轮实测：七份共享头 + `main.cpp` **逐字节相同**（基线提交 `b5d94d6` 与当前工作树
哈希一致 `a0ea5d9c…`）⇒ **零位移成立**。

> 门禁写好后才发现：`main.cpp` 在门禁里**根本进不来**（缺 `esp_task_wdt.h` /
> `Preferences.h`，那是 ESP-IDF/Arduino 的东西）——而它恰恰是板名/能力宏最容易
> 泄漏、却最没人看的文件。补了两个替身（`sim/compat/`）把它纳进来。
> 这正是"先立门禁"的价值：没有它，我上一版的"零位移证明"是**空跑**（两边都是空文件）。

## 九、经验（本轮新增）

1. **跨后端的数据格式差异，必须用"设备侧已知输入 → 读回原始字节"钉死**：
   仿真是另一套后端，永远验不了驱动的转换。
2. **探针自己也会错，且错起来像产品坏了**：探针必须有控制组（画已知色读回），
   并且**不做任何颜色换算**（用调色板常量直比）。
3. **几何不许依赖"当前语言/当前状态"**：常驻元素按最宽的那种情况留位。
4. **门禁要能容纳"新平台"**：能力宏 + 预处理哈希基线，比"每次人工比对反汇编"可靠。
5. **删测试的错误理由特别危险**："在测一个不存在的分支"（v0.5.1）和"查一个不存在
   的文件"（同上）—— 功能被砍时删掉的应该只是**能力**，不是**门禁**。

## 十、补记（第二轮）：紫色没修掉 —— 交换调在了错误的对象上

第一版的修法写成了 `tc.prepareTile(buf, n)`，而 `tc` 是 **TileCanvas**（继承 `Gfx`
基类）——命中的是基类的空实现，**交换静默不发生**，真机照旧紫色。`GfxM5` 的覆写
要由**显示后端对象** `g` 才能走到，即 `g->prepareTile(buf, n)`。

**为什么当时所有检查都是绿的**（这一节比 bug 本身重要）：

1. **设备自检自己在造机制**：`BLITCHK` 是在 `GfxM5` 对象上直接调 `prepareTile` 再推
   图案比对的 —— 它验的是"这个机制本身对不对"，而**产品路径根本没走这条**。
   修法：新增 `BGPATH` 自检，走 `eraseDirty`（游戏真实擦格）→ `cellTile` → 后端
   `pushImage`，选一个"路"格（症状正好出现在敌人走过的路上），逐像素对比直画。
2. **仿真的 A/B 断言盖不住**：`GfxFb`（仿真后端）本来就不需要交换（no-op），所以
   "tile vs 直画逐像素相同"在仿真里恒真 —— 这条断言证明的是**内容**一致，不是
   **字节序**一致。
3. **门禁缺一条**：仿真里没有任何断言要求"块缓存必须交给后端整理过"。现在补上了：
   `GfxFb::prepareTile` 计数，仿真断言"走一次 `eraseDirty` 后计数必须增加"。
   已做**双向证伪**：把 `g->prepareTile` 改回 `tc.prepareTile`，门禁立刻变红
   （`计数 0->0 未增`），改回来即绿。仿真 **438 passed / 0 failed**。

教训（写进经验清单）：**探针必须走产品的真实入口**；"自己造机制自己验"得到的是
绿灯，不是证据。凡是要断言"某条路径真的执行了"，就用**计数器**（仿真侧）或
**渲染结果对比**（设备侧），不要断言"我调用的那个函数返回正确"。
