# FIXLOG v0.5.2 — 波次压叠雪崩（L10 第 2 波没打完就自动开第 3、4 波 → 帧预算崩）

> **本文是 v0.5.2 的工作档案**：做了什么、发现什么问题、怎么修的、踩过什么坑、下次开工从哪继续。
> 与 `docs/HANDOFF-PROMPT.md`（权威交接提示词）冲突时，以那份为准；本文是它的论据库。
> 触发：**用户真机报告** —— "第 10 关有 bug，第二波敌人没有打完就自动开始第三波、第四波，
> 然后就性能不够，死机了"。
> 版本号：v0.5.1 → **v0.5.2**（一个真 bug 的定点修复，不跳号）。

---

## 一、做了什么（一句话）

把"压叠窗口"的判据从**场上总敌数 ≥ 8**（分不清残留是哪一波的）改成
**本波出生的幸存者 ≤ 本波的一半** + 一条**场上总数硬红线**（≥16 不压叠），
雪崩消失：L10 弱防真人复现台上峰值在场 **48 → 16**、每帧 fillRect **3459 → 1557**；
仿真断言 **303 → 318**（tab5）/ **305 → 320**（claw4），两个 profile 全绿。

## 二、复现（先复现，再改）

用真固件源码（`game.h`/`render.h`）搭了一个"弱防真人"复现台（PC，非另写模拟器）：
`L10 + 3~8 座 1 级机枪 + 不主动按 NEXT WAVE`，逐波记录**开波前一刻**的敌人构成
（本波残敌 / 旧波残留）与每帧绘制调用量。

复现结果（**修前**，L10，3 塔，7 分钟）：

| 开波 | 开波前本波残敌 | 旧波残留 | 在场 | lives |
|---|---|---|---|---|
| w2 | 0 | 0 | 0 | 20 |
| **w3** | **9 / 9（一只没死）** | 0 | 9 | 20 |
| w4 | 10 / 10 | 9 | 19 | 20 |
| w5 | 11 | 19 | 30 | 20 |
| w6 | 13 | 28 | 41 | 18 |
| w7 | 13 | 32 | 45 | 14 |
| w8 | 13 | 33 | **46→48（MAX_ENEMIES 硬顶）** | 8 |

- **第 2 波 9 只刚刷完、一只没死，5s 后就开了第 3 波** —— 正是用户描述的第一症状。
- 之后每一波都踩着前几波的残留再次满足判据 → 波波叠到 **48（MAX_ENEMIES）硬顶**。
- 每帧 fillRect：正常波 **424** → 拥堵 **4192**（≈10×）；每帧像素 74k → 599k。
- 299s 时 lives 归零：玩家是在"一张糊满敌人的幻灯片"里输掉的。

## 三、根因

`src/game.h` 的压叠窗口（v0.3.2 引入）判据是：

```cpp
if (alive >= 8) { ... 5s 后强开下波 ... }   // alive = 场上所有 active 敌人
```

`alive` 数的是**全场敌人**，**不区分这 8 只是哪一波出生的**。于是：

1. **小波被误判成"清完"**：第 2 波 `waveSize(2)=9` 只，刷完时一只没死 = 9 ≥ 8 → 立刻满足。
2. **踩残留自锁**：新波一开，旧波残留还在场上，下一轮 `alive` 只会更大 → 判据**更容易**满足
   → 雪崩一旦开始就再也回不来，直到撞上 `MAX_ENEMIES` 硬顶。
3. 硬顶之后 `spawnEnemy()` 找不到空槽 → `toSpawn` 永远 >0 → 波次逻辑失去意义，
   只剩一堆同屏敌人把帧预算烧光。

真机为什么表现成"死机"而不是"卡"：这台机器的帧预算本来就紧，而本机型**已经有过一次同类前例**
——v0.4.3 修的 `drawOnboard` 每帧 14,400 次 fillRect 写 PSRAM 帧缓冲，与 DSI 扫描 DMA 抢 cache，
最终死锁在 `esp_cache_msync` 自旋锁 → loopTask 卡死 >8s → task WDT panic（见 `src/main.cpp` 注释）。
本次拥挤期是 **4192 次/帧 ≈ 前例的 29%**，叠加音频派发（3 条 playRaw/帧，标称 ~4ms/帧）后
跌破 30fps，观感即"性能不够、死机"。⚠️ **这一条是机制推断（有前例、有量级），没有真机串口实证**
——按用户偏好不走串口调试，真机结论留待刷机后的实际手感。

## 四、修法（三个常量 + 一处判据 + 一个字段）

`tools/layout.py`（数值真源）：

```python
OVERLAP_MS           = 5000   # 不变
OVERLAP_LEFTOVER_PCT = 50     # 本波幸存者 ≤ 本波规模的一半才算"清完"
OVERLAP_LEFTOVER_MIN = 2      # 小波兜底：至少留 2 只余量，别为了最后一只卡住
OVERLAP_FIELD_MAX    = 16     # 场上总数 ≥ 此值 → 不压叠（帧预算红线）
```

`src/game.h`：

- `Enemy.waveTag`（+1 字节）：出生波次。**三条出生路径都写**（`spawnKind` / `broodSpawn` /
  `splitDeath`）——产卵与分裂体算本波，不能外挂（漏一处就会重演"数不清是谁的"）。
  用 `uint8_t` 安全：`ENDLESS_WAVES=250 < 256`，比较时两侧同款强转。
- `waveSurvivors()`：只数 `waveTag == 本波` 的在场敌人。
- `overlapQuota()`：`waveSize(w) * 50%`，下限 2 只。
- 判据：`alive < OVERLAP_FIELD_MAX && waveSurvivors() <= overlapQuota()`。
- **两条铁律原样保留**：末波绝不压叠；`s_overlapUntil` 绑 wave 且换关复位。

设计取舍（**旋钮在 `OVERLAP_LEFTOVER_PCT`**）：
- 先试过 `15%`（"几乎清完才压叠"）——被判据反噬：塔要等最后几只血厚的残兵，
  正是 v0.3.2 想消灭的"塔永远集火单只、溢出伤害全浪费"。证据：仿真 L7/L10/L12 三关
  bot 从"过"变"不过"。**50% 是"本波过半已清"**，既不让"0 杀就开下一波"发生，
  也不把收尾拖长。
- `OVERLAP_FIELD_MAX=16` 是**安全网**，不是主判据：正常一波（`waveSize(15)=28`）本来就会
  同时在场 19~22 只，所以它只在"玩家已经落后、场地明显堆起来"时生效。
  代价是极端情况下波次会等场地清一点再开——这是**安全的失败模式**（不会烧帧预算），
  而旧行为是相反的（堆到硬顶）。

## 五、证据（修后）

| 场景 | 修前 | 修后 |
|---|---|---|
| L10 弱防（3 塔）峰值在场 | **48（硬顶）** | **16** |
| L10 弱防峰值 fillRect/帧 | 3459 | 1557 |
| L10 一般玩家（≤8 塔）峰值在场 | 48 | 26 |
| L10 第 2 波 → 第 3 波 | 9/9 全在，5s 后强开 | 本波剩 ≤4 只才开（`9*50%=4`） |
| 波次推进 | 雪崩（每波踩残留） | 每波过半已清才压叠（实测 w9 开波时本波 8/19 在场） |

仿真门禁：**tab5 318 passed / 0 failed**、**claw4 320 passed / 0 failed**、24bpp 内核测试 OK。
新增断言：
- §14①：本波只剩 2 只（≤ quota）→ ~5s（150 帧）后强开下波（**保留原意图**）。
- §14② **反例（本次 bug 的回归）**：本波 8 只全在场上 → 5s 内**绝不**强开。
- §14③：本波只剩 2 只、但场上总数 ≥ `OVERLAP_FIELD_MAX` → 仍不压叠（帧预算红线）。
- §14b：L10 弱防 3 塔跑 7 分钟，峰值在场必须 `< MAX_ENEMIES` 且 `≤ 32`。

## 七、经验（下次别再犯同一族）

1. **计数型判据必须回答"数的是谁"**：`alive >= 8` 里的 `alive` 是"全场"，但写这条的人心里想的
   是"这一波的残敌"。同类形状的坑还有一堆：`g_w.score`（累计击杀）当"本波击杀"用、
   `spawnedOfWave` 当"本波剩余"用。**只有身份（waveTag）能回答身份问题。**
2. **任何"压力阀"都要配一条负载上限**：只要一个规则能反复触发（每波都能满足），就必须有
   一个能把它关掉的上界（这里是 `OVERLAP_FIELD_MAX`），否则它一定会找到那个硬顶。
3. **门禁要写反例**：§14 只有正例（"≥8 只就该压叠"），于是把错误语义焊死在测试里
   （旧断言换个波量就会亮）。本次补了 ②③ 两条**反例**断言——反例才是抓回归的那一半。
4. **先量再改**：判据从 15% 改到 50% 不是拍脑袋，而是"仿真里 bot 三关由过转不过"逼出来的；
   没有复现台的 fillRect/帧 仪表，只会讨论不出结论。
