## 二、问题清单（按严重度）

### P0-1　中文开机标题只渲染出"塔防"——三个字的点阵从没被生成过 ✅已修+有回归

- **现象**：中文模式下开机标题行显示为"塔防"，"像素"两个字是空白。
  （用户看不到：默认语言是英文，只有手动切到中文才暴露。）
- **根因**：`drawTitle` 里写的是 `px_textCenter(g, ..., "像素塔防", ...)`——**硬编码中文字面量**。
  而字库生成器 `tools/gen_cnfont.py` 的收字来源是 **`i18n.h` 的 `STR_CN` 表**。
  硬编码字符串不在表里 → 生成器看不到 → 这几个字根本不在 `cn_font.h` →
  `px_cnChar` 找不到字形，**静默跳过**（既不崩、也不报错、编译器更不管）。
- **同类**：英文模式下"中文"按钮标签同样硬编码，于是"文"字缺——**中文按钮在英文界面上
  是个空框**（v0.4.2 发布版真机上就是这个样子）。
- **修法**：① 新增 `STR_TITLE_CN`（"像素塔防"）/`STR_LANG_EN`（"ENGLISH"）/`STR_LANG_CN`
  （"中文"）三条走表；② 渲染代码里改用 `TR(...)`；③ 在 `i18n.h` 头注写死纪律：
  **"渲染代码里不允许出现硬编码中文"**。
- **回归**：`pixel_text.h` 新增全局缺字计数器 `s_cnMissing`；`sim/run.cpp` 的中文模式下把
  **每个界面真画一遍**（标题/选关/战斗/面板/结算/失败/引导三步/提示条），断言计数器归零。
  这条防线是**通用**的：以后任何硬编码中文都会让 CI 红，不需要有人记得去查。

### P0-2　一整类全角标点同时躲过生成器和 CI 检查器 ✅已修+规则收紧

- **现象**：`已击败：` 少冒号、`第3步/3 - 拦住所有敌人！` 少感叹号——表现为文字后面一个
  小空档，肉眼极易当成"排版如此"。
- **根因**：**收字谓词写成了字符集范围**。生成器与检查器各自都写了
  `if "\u4e00" <= ch <= "\u9fff"`（只收 CJK 汉字区），而 `：`(U+FF1A) 和 `！`(U+FF01)
  在全角标点区——**两个文件用同一条错误的规则，所以互相验证不出问题**。
  正确的谓词应该按**渲染路径**定义：`px_text` 遇首字节 `>= 0x80` 就切点阵 → 那么
  **STR_CN 表内每一个非 ASCII 字符都必须有字形**，不管它是汉字还是标点。
- **修法**：新建 `tools/cn_glyph_rule.py` 作为**收字规则单一真源**（`needs_glyph()` =
  `ord(ch) >= 0x80`），生成器与检查器都 import 它。字库 92 → **99 字**。
- **教训**：**同一个不变量被复制到两个文件里，迟早漂移**；而且"两边都错得一样"时，
  交叉校验是无效的。

### P1-1　标题界面 LANGUAGE 标签压住 ENGLISH 按钮 26px ✅已修+有断言

- **现象**（用户点名的那一处）："LANGUAGE" 右端伸进 "ENGLISH" 按钮里。
- **根因**：`px_text(g, 360, ..., TR(STR_LANG), 2)`——硬编码 x=360，8 字符 × 12px = 94px
  → 右缘 454；而 `LANG_EN_X = 430`。**26px 重叠**。
- **修法**：改为**按钮组上方居中**（`px_textCenter`）。为什么不改成"按钮左侧留够宽度"？
  因为按钮的左缘会随语言切换（ENGLISH 8 字符 vs 英文 2 字）而看起来跳动，居中放置同时
  解决重叠与跳动。标签 y 提为宏 `TITLE_LANG_LBL_Y`，并有断言守"标签底边（按 16px 中文
  点阵算）不得贴按钮顶边"。

### P1-2　无尽模式 BEST 数字压住 WAVE 标签 ✅已修+有断言

- **现象**：无尽模式下 HUD 显示 `BEST 42WAVE 9/250`——"42" 正好叠在 "W" 上。
  **1/4 缩放的 contact sheet 上完全看不出来**，必须放大或数像素。
- **根因**：`BEST` 标签画在 x=770、数字跟在后面 → 数字区间 799..813；而静态 HUD 的
  `WAVE` 标签**固定在 x=800**（在 `drawBackground` 里画，与 `drawHud` 分属两个函数）。
  两个函数各画各的，谁也不知道对方占了哪。
- **修法**：BEST 移到 `HUD_BEST_X = 640`（在 GOLD 擦除框 626 之后、WAVE 标签 800 之前
  的空档里），并断言 `BEST 右缘 < HUD_WAVE_LBL_X`。

### P1-3　金币符号 `$` 每帧被擦掉——v0.4.2 引入的回归 ✅已修+有断言

- **现象**：HUD 上金币数字前面**没有 `$`**。肉眼看到"210"不会觉得缺什么——这是最难
  发现的一类。
- **发现方式**：不是我"看"出来的，是**数像素**数出来的：统计 (418..440, 18..44) 区间内
  金色像素数量 = **0**。
- **根因**：v0.4.2 加 SIEGE 警示条时写了
  `g->fillRect(300, 14, 180, FONT_H*3+6, C_UI_BG)`——清空框铺到 **x=480**，而静态 HUD 的
  `$` 画在 **x=420**。`drawHud` 每帧执行这行，于是 `$` 每帧被擦。
  **`$` 从 v0.4.1 就在 420，SIEGE 是 v0.4.2 加的** —— `git log -S "fillRect(300, 14"` 确认
  这行只出现在 v0.4.2 那个提交里。
- **修法**：清空框收窄为 `HUD_SIEGE_X=300 / HUD_SIEGE_W=112`（够放 `BUILD ZONE LOCKED`
  101px，右缘 412 < 420），并加两条断言：`SIEGE 条右缘 <= $ 起点`、`$ 右缘 <= GOLD 擦除框`。
- **为什么之前没发现**：v0.4.2 的验收只看"标题界面出来了 + 引导 + 无尽按钮"，HUD 细节
  没人逐像素对。**这条正是"必须让机器数像素"的典型**。

### P1-4　L20 通关画面的 ENDLESS MODE 按钮底边埋进建造栏 ✅已修+有断言

- **现象**：按钮第二行 `SURVIVE 250 WAVES` 被建造栏槽位盖掉一半。
- **根因**：`ENDLESS_BTN_Y = 590` 硬编码，按钮高 64 → 底边 654，而 `BUILD_BAR_Y = 640`。
  **压进去 14px**。绘制顺序上 `renderFrame` 先画建造栏、`updateOverlays` 后画通关面板，
  所以按钮压在槽位**之上**——真机同样是坏的。
- **修法**：`ENDLESS_BTN_Y` 改为**从建造栏反推**：
  `(BUILD_BAR_Y - ENDLESS_BTN_H - 16)` = 560；并抽出 `CLEAR_PANEL_Y` / `CLEAR_PANEL_H`
  常量，断言"按钮上不压面板、下不压建造栏"——任何一边几何改动都会立刻红。

### P1-5　标题界面「点击开始 / TAP TO START」重影——同一条文字画了两遍 ✅已修

- **现象**（**用户在真机上发现的**，本轮前面所有截图评审都漏了）：开机标题界面底部那行
  "点击开始"/"TAP TO START" 看起来糊成两层、像烫金没对准。中英双语都有。
- **根因**：`drawTitle` 末尾把同一条文字画了**两遍**，想做"双色叠字描边"：
  ```c
  px_textCenter(g, SCREEN_W/2,     580, TR(STR_TITLE_HINT), C_BTN_HI,  3);  // 亮
  px_textCenter(g, SCREEN_W/2 - 3, 580, TR(STR_TITLE_HINT), C_TEXT_DIM, 3);  // 暗，左移 3
  ```
  两个错误叠在一起：
  1. **顺序反了**。暗层是**后画**的，于是它把整条字身盖成暗色，只在最右缘漏出 3px
     亮边——玩家看到的"主体"其实是暗色层。
  2. **偏移量没有意义**。字模是 5×7 放大 3 倍 → 笔画宽 3px、笔画间距也是 3px 量级；
     左移 3px 后，亮层的笔画**正好落进暗层笔画的缝隙里**，两层互相穿插。
- **为什么"把顺序翻过来"也不对**：我先试了交换两行（暗在下、亮在上）——**依然是糊的**，
  因为问题不只是顺序，而是**这个字号根本没有做描边的余量**。描边要求偏移 < 笔画间隙
  才有"边"；这里是 3px vs 3px，怎么排都是重影。
- **修法**：**只画一次**（亮色）。星空是深底，亮色对比度本来就够，不需要描边。
- **教训**：
  1. **"描边/阴影"不是免费效果**，它的可用性由字模分辨率决定。5×7 放大 3 倍的点阵里
     没有 1px 级的余量，任何 sub-笔画偏移都只会变成重影。小字模想要轮廓，只能靠
     **换成更大的字模重新光栅化**，不能靠叠画。
  2. **两次画同一条文字 = 两次 `s_cnMissing` 累加、两次宽度计算**，但缺字计数器和
     宽度断言都不会报错——**这类 bug 断言抓不到，只能靠人眼**。这也是 `--shots`
     为什么要**逐张目检**而不是只跑一遍断言：本轮 22 张我全看了，却恰恰漏了这张
     里最显眼的一处（因为我的注意力在"有没有溢出容器"而不是"字本身干不干净"）。
     **下次改 UI，先把图放大到 2–3 倍看笔画，再看边界。**

### P3-2　（工具坑）刷进去了却没跑：残留 app 分区把 bootloader 带跑偏 ✅已定位

- **现象**：`write-flash 0x0` 报 `Hash of data verified`，但真机花屏、一会儿蓝屏。
- **第一次误判**：我以为是回读失败、以为是自己的代码写坏了，反复重试刷机——
  用户直接点破："**现在这个 rom 不是你的程序啊**"。
- **根因**：`esptool write-flash` **只写镜像覆盖到的地址范围**，并且**跳过全 `0xFF` 的块**——
  它**不会擦掉其他 app 分区里的旧固件**。本项目的分区表是
  `app3M_fat9M_16MB.csv`（存在第二个 app 分区），这块板以前烧过别的项目，
  残留固件一直在；bootloader 按 otadata 选分区，就跑去跑那份残留了。
  所以"花屏 + 蓝屏"**跟 v0.4.3 的源码毫无关系**——是别人的程序在跑。
- **修法**：刷机前先 `esptool erase-flash` 擦整片，再写 merged 镜像。写入后串口
  横幅从 `DEEPFIRE v0.1.4` 变成 `=== PIXEL TOWER DEFENSE v0.4.3 | board=22 | 1280x720 ===`，
  游戏正常停在标题界面。
- **教训**：
  1. **`esptool` 的 "Hash of data verified" 只证明"写进去的和文件一样"，
     不证明"启动的是这份"。** 验证刷机生效的唯一可靠信号是**启动横幅的版本串**。
  2. **"刷机成功"和"程序跑起来"是两件事**，中间隔着分区表 + otadata。
     手工打包的发布镜像要配套写"先擦除"；M5Burner 默认 `eraseAll` 所以没这个问题。
  3. **别在没拿到证据前反复操作硬件**——我重试刷了两次，用户得看着屏幕被反复覆盖。
     先取证（串口日志），再动手。
- **副作用（要如实记录）**：全片擦除**清掉了 NVS**，所以这次是真的"全新安装"
  ——`unlock=0001 cleared=0000 lang=EN`，之前的关卡进度没了。

### P2-1　开局提示条压在建造栏第 3–4 槽 → 判定为死代码，**整段删除** ✅已删

- **现象**：`TAP GRASS TO BUILD TOWER` 白字盖在 FROST/ENERGY 槽上。
- **根因**：`drawReadyHint` 锚在 `y = SCREEN_H - h - 14 = 692`（屏底），建造栏从 640 开始。
- **更深一层**：`drawReadyHint` 在**产品代码里没有任何调用点**——v0.4.2 用引导 overlay
  取代它之后忘了删。它是**死代码**：唯一还在"使用"它的只有 `--shots` 批处理和
  `checkUiTextFit()` 自己的断言。
- **处理（尾单）**：先只把 y 修到建造栏上方，然后**整段删除**——函数、`STR_READY_HINT`
  枚举项、两张语言表条目、以及为它写的那 4 条断言全部移除。
  **理由**：给死代码写断言是最坏的一种"维护"——它让死代码看起来被照顾着，还挡住了
  "这个函数根本没有调用点"这个唯一重要的信息。留着"以后可能用"的坐标只会再次腐烂。
  真要轻提示时重新引入即可，但底部锚点必须是 `BUILD_BAR_Y` 而不是 `SCREEN_H`。
- **副作用可控**：字库 99 字不变——`点草地建塔` 是 `第1步/3 - 点草地建塔`
  （`STR_ONBOARD_1`）的字符子集，删掉它不减少任何字形。仿真 374 → 370（−4 条断言）。
- **教训**：**死代码不会自己报告"我坏了"**。是**截图批处理（`--shots`）把它画出来**才
  暴露的——顺带说明批处理模式本身有价值。发现死代码的正确动作是删，不是修。

### P3-1　（工具坑）截图批处理把 overlay 叠在上一屏残影上 ✅已修

- **现象**：第一版 `--shots` 产出的"引导 overlay"截图里，底下压着上一个界面（Game Over
  面板 + 通关画面上残留的 ENDLESS 按钮）。
- **根因**：`drawOnboard` / `drawGameOver`（以及当时还在的 `drawReadyHint`）都只画自己
  那一块，**指望底下已经是一张完整帧**；而批处理是按顺序连续画、没有重铺底帧。
  绘制顺序上 `renderFrame` 先画建造栏、`updateOverlays` 后画通关面板，所以按钮压在槽位
  **之上**——真机同样是坏的。（这条同时验证了 P1-4 是真 bug，不是批处理假象。）
- **修法**：批处理加 `freshBoard(lv)` 助手——`levelLoad` + `drawBackground`（内部
  `fillScreen`）+ HUD/建造栏/按钮/实体，每个界面截图前先铺干净底。
- **教训**：**截图评审工具本身要有"干净底帧"语义**，否则它产出的脏图会浪费一轮排查
  （我确实先怀疑了产品，再回头怀疑工具）。

## 四、经验（下次别再交学费）

1. **硬编码中文 = 字库漏洞**。字库的收字来源是字符串表，绕过表就等于绕过生成器。
   纪律已写进 `i18n.h` 头注，并加了"缺字计数器 + 全界面中文渲染断言"做机器看守。
   **推论**：任何"从源码自动派生资源"的设计（字库/PCM/配置）都必须有"渲染/使用时
   报告缺件"的反向信号，否则漏件是静默的。
2. **收集谓词要按渲染路径定义，不要按字符集范围定义**。写 `>= 0x80` 就不会漏；
   写 `U+4E00..9FFF` 就一定会漏掉标点、假名、符号、emoji。规则写在**一处**，
   生成器与检查器共用——"两边各写一遍"是最坏的一种去重：错得一样就永远查不出来。
3. **清空框（erase box）必须和它的邻居一起被断言**。`fillRect` 的宽度是按"最长旧内容"
   定的，但它顺手也会擦掉任何落在里面的**静态**元素（本例的 `$` 是 `drawBackground`
   画的，`drawHud` 根本不知道它在哪）。凡是"擦一块、画一块"的代码，都要有一条
   "这块不许压到别人"的断言。
4. **散落的绝对 x 坐标是重叠的温床**。这轮 7 个 bug 里有 4 个是"两个函数各自硬编码
   x，加起来越界"。收敛为 `HUD_*` / `*_BTN_*` 命名常量后，断言和绘制引用同一批宏，
   改一处不会再漏另一处。**顺带**：静态 HUD 标签原本在 `drawBackground` 与射程框
   重画两处复制，已抽成 `drawHudLabels()`。
5. **有些缺陷只能靠"数像素"发现**。`$` 被擦、BEST 压 WAVE 都是 1/4 缩略图上完全
   看不见的。做法：对关键区域做颜色/区间统计（几行 Python），把"看起来没问题"
   变成"有数字支撑"。这也是为什么本轮最终把它们固化成了断言而不是"下次注意看"。
6. **截图工具要有干净底帧语义**。overlay 类函数只画自己那块，叠在残影上会产出误导性
   图片——先怀疑工具，再怀疑产品（但残影本身也可能正好暴露真 bug，别急着修工具）。
7. **检查强度要匹配生成物可复现性**（v0.4.2 的教训继续适用）：中文点阵是外部字体光栅化
   的产物，CI 只能查语义不变量（覆盖/几何），不能查字节。本轮把这条不变量**收紧**了
   （非 ASCII 全覆盖），但依然是语义级。
8. **版本号纪律**：v0.4.2 已发布（tag + GitHub Release），所以这轮修复自然落到 **v0.4.3**
   ——bug 修复轮也走 patch 号，不因为"改动多"就跳号。
9. **【最该记住的一条】断言能守住"边界"，守不住"内容"。** P1-5（标题"点击开始"重影）
   是**用户在真机上发现的**：我 22 张截图全看过，`checkUiTextFit()` 全绿，缺字计数器为 0
   ——因为我当时只问"这行字有没有超出容器"，没问"这行字本身干不干净"。同一行画两遍，
   宽度断言算的还是同一个宽度，计数器照常计数，**两条防线同时失效**。
   **纪律**：改用 `--shots` 出图后，**先把关键区域放大到 2–3 倍看笔画**（看有没有重影/
   错位/漏色），**再看边界**。像素风游戏的视觉缺陷藏在笔画层面，缩略图一律看不出来。
   另外——**自动化防线越完备，越容易让人停止看**。本轮这是个真实的教训。

5. **【新发现，未修】中文不随 scale 放大，导致大标题处中英视觉严重失衡。**
   `pixel_text.h` 的设计注释写着"中文固定 16x16（不随 scale 放大）：与 **scale3** 的
   ASCII（15x21）高度协调"——这条约定只在 scale≈3 时成立，但代码里实际用了
   scale 1/2/3/4/6：

   | 调用点 | scale | 英文实际高 | 中文实际高 | 观感 |
   |---|---|---|---|---|
   | `STR_LEVEL_CLEAR`（通关标题） | 6 | 48px | **16px** | 中文小得不像标题 |
   | `STR_GAME_OVER`（失败标题） | 6 | 48px | **16px** | 同上 |
   | `STR_SELECT`（选关标题） | 4 | 32px | **16px** | 差一倍 |
   | `STR_ENDLESS`（无尽按钮） | 3 | 24px | 16px | 基本协调 ✅ |
   | `STR_ENDLESS_DESC`（按钮副标题） | 1 | 8px | **16px** | 中文反而大一倍 |

   机制：`px_text()` 把 scale 传给了英文分支 `px_char(...)`，但中文分支
   `px_cnChar(g, x, y, s, c)` **不接 scale**，`CN_ADV` 也固定 17px。
   修法与取舍见 `docs/`——**需要你拍板**：
   - 方案 A：`cnScale = (scale + 1) / 2`，中文随 scale 走（scale 2/4/6 → 16/32/48px，
     与英文 16/32/48px 精确对齐）。代价：所有中文界面字号变化，需重排若干 y 坐标
     并用 `--shots` 逐张复核；"放大会糊"的顾虑在像素风下可接受。
   - 方案 B：保持中文固定 16px，把大标题在中文模式下改用更小的 scale——
     中文标题仍只有 16px，720p 上偏小，治标不治本。
